## 1. 最终能玩到什么

项目暂名 **TinyGameNet / 联机小操场**。

你先启动一个 C# 控制台服务器，再打开两个 Unity 游戏窗口。两个玩家输入昵称和服务器地址，进入同一块俯视场地。每个人只能控制自己的角色，两边都能看到所有人的位置。

场地上有一块终点区域。玩家走进去后，由服务器加一分并把他放回出生点；双方看到相同的分数。有人退出，其他人的画面移除他的角色。

第一版支持 Windows、一个房间、2～4 名玩家，先在一台电脑上运行，再在家庭局域网验证。角色只在 X/Z 平面移动，边界由简单坐标判断，暂不涉及跳跃和复杂物理。

这是一个持续扩展的项目。网络连接、消息协议、服务器世界和 Unity 画面都会由你逐步搭起来。

## 2. 为什么现在适合这样学

根据前面聊天与实验，已有的起点是：

| 已有证据 | 对接下来教学的影响 |
| --- | --- |
| 做过 ByteStream、重组器、TCP 收发端，能讨论 ACK 与窗口 | 不重新实现 TCP；直接把这些知识用于理解 Socket 的保证与限制 |
| 能说明客户端副本、所有权与服务器权威 | 从输入怎样进入服务器开始，把概念落实到具体状态 |
| 对 `Task`、`await`、Socket API 曾多次追问 | 每个新 API 先讲谁调用、返回什么、完成意味着什么 |
| 曾因不知道整个实验的结构而卡在填函数 | 每步先看完整小流程，再从空文件写出这个功能 |
| 对 GameFrameX 的接口层次还不熟 | 自己实现一个机制后，只对照它解决同一问题的几段源码 |

这些证据不等于已经能独立完成项目。当前最需要确认的是：能否自己串起对象、异步操作和调用顺序。我们在前两个里程碑里边做边确认，无需重做一套理论考试。

## 3. 三个进程怎样分工

```text
Unity 客户端 A ── TCP 连接 A ──┐
                              ├── C# 服务器：唯一的游戏世界
Unity 客户端 B ── TCP 连接 B ──┘
```

- 客户端：采集方向键，发送输入，接收状态，创建和移动画面中的角色。
- 服务器：记住每条连接对应哪个玩家，推进移动、检查边界、判定得分，发送世界状态。
- 同一条 TCP 连接双向使用。客户端向服务器发输入，服务器通过这条连接返回消息。

网络框架负责连接与消息运输。游戏规则负责移动与得分。以后换成“联机背包”时，连接和拆帧部分应当还能复用。

## 4. 技术选择

| 部分 | 第一版选择 | 原因 |
| --- | --- | --- |
| 客户端 | Unity 2022.3、C#，Windows 桌面 | 你已有的环境，能专注消息与画面的关系 |
| 服务器 | 独立 .NET 10 控制台程序 | 本机已安装 10.0.302 SDK，服务器无需启动 Unity |
| 共享代码 | 兼容 .NET Standard 2.1 的普通 C# | Unity 和服务器使用同一份协议及网络代码 |
| TCP 入口 | `TcpListener`、`TcpClient`、`NetworkStream` | 先用已接触的 API；后续对照 GameFrameX 的 `Socket` 封装 |
| 异步 | `Task`、`async/await` | 等待网络时不堵住游戏更新；不假设 `await` 后必定在哪个线程 |
| 消息边界 | 自定长度前缀与小包头 | 实际处理任意分批读取，复用第 24、25 课的知识 |
| 业务内容 | M3 开始使用 Protobuf | 用 `.proto` 定义字段并生成 C# 消息类，靠近 GameFrameX 的序列化方案 |
| 输入与显示 | 简单方向输入、俯视相机、角色标记 | 非网络场景搭建由我协助准备，你掌握输入到网络的连接部分 |

已只读核对旧项目：`D:\unityGame\My project (14)` 使用 `2022.3.42f1c1`。新项目建议放在 `D:\unityGame\TinyGameNet`，正式创建时检查是否已有同名目录。

共享代码的 API 范围与服务器运行时是两件事。服务器可以跑 .NET 10，但共享源码不随意调用 Unity 不支持的 .NET 10 专用 API。Unity 2022.3 提供 .NET Standard 2.1 兼容级别，见 [Unity 官方说明](https://docs.unity3d.com/2022.3/Documentation/Manual/dotnetProfileSupport.html)。

Protobuf 的运行库与生成工具版本将在 M3 安装前固定，并验证 Unity 编辑器和 Windows 构建；当前没有声称这些依赖已装好或已测试。

## 5. 八个里程碑

每个里程碑拆成若干次 20～45 分钟的小任务。表里的时间包括解释、自己写代码和调试，不是要求一次连续做完。

| 阶段 | 遇到的问题与新增机制 | 你能看到的结果 | 预算 |
| --- | --- | --- | ---: |
| M0：画面与责任 | 一个角色的位置由谁保存？搭好场地，区分输入与显示 | 本地小人能移动；能指出以后由服务器接管哪一行 | 2～3 小时 |
| M1：两个进程交换字节 | 内存不能跨进程共享；使用 TCP 建连和一次收发 | Unity 发 `hello`，控制台服务器收到并返回 | 3～5 小时 |
| M2：完整消息 | 一次读取可能只有一部分消息；加入长度前缀与读取循环 | 拆开写、连续写两条，都能还原正确消息 | 4～6 小时 |
| M3：消息对象 | 一串字节怎样表示具体业务？引入包络与 Protobuf | 发出加入请求，收到带玩家编号的响应 | 3～5 小时 |
| M4：多个玩家 | 两条连接不能混为一个玩家；加入会话和世界列表 | 两个 Unity 窗口都看到两名玩家，后加入者也看到完整世界 | 3～5 小时 |
| M5：服务器移动 | 不能按收到的消息条数决定走多远；加入固定步长模拟 | A 按键，两边都显示服务器计算的 A 的位置 | 5～8 小时 |
| M6：游戏与生命周期 | 得分谁说了算？进程退出后状态怎么办？ | 服务器判分；角色断线被移除，停止服务器有可读提示 | 4～6 小时 |
| M7：整理与对照 | 业务代码和网络代码开始重复；抽出小框架 | 请求关联、超时、通道 API 清楚；能对照 GameFrameX 解释差异 | 4～6 小时 |

预计核心学习 28～44 小时，再留 2～6 小时处理环境和实际暴露的困难，总预算 **30～50 小时**。按每天 2.5 小时，约 12～20 个学习日；按八阶段细化后，第一次看到双人移动大约在 20～30 小时附近。前两个阶段结束后重估。

## 6. 每一步怎样教、怎样写

一次推进只围绕一个可观察结果，例如“服务器收到一条完整消息”。

1. 先给完整小情境，标清消息从哪个对象到哪个对象。
2. 说明本次需要新增哪些状态、修改哪些文件，以及每个函数由谁调用。
3. 把涉及的 API 用最小例子讲清楚；陌生 C# 语法当场补，不提前堆满一章。
4. 由你从空文件写出一小段完整功能。我提供递进提示和必要注释。
5. 运行后看日志或画面；失败时沿刚画出的路径找原因。
6. 你能结合情境说明它怎样工作，就继续。代码中的心得足够，不要求单独报告。

公开函数提供必要的 XML 注释；复杂函数先在注释里写处理顺序。不会只给一个方法名就要求你猜整个设计。

我负责把非网络场景、工具配置和生成命令准备清楚。网络逻辑的关键决定和调用过程由我们一起推导；如果我代写一段，会明确指出你必须看懂的部分。

## 7. 第一版怎样算完成

- 一个服务器、两个 Unity 客户端能重复启动和关闭。
- 双方看到相同的玩家集合、权威位置和分数；后加入者收到当前状态。
- 修改客户端显示位置不会改变服务器位置；客户端也不能通过报别人的编号控制别人。
- 输入消息发得更多不会提高移动速度；服务器每个模拟步最多推进一次该玩家。
- 多条应用消息连续到达、长度前缀被拆开、正文未收全时，解析结果仍正确。
- 非法长度在分配大块内存前被拒绝；慢客户端不会让服务器无限积压发送数据。
- 关闭客户端会移除玩家；强制终止等无法及时检测的情况由后续活动超时策略收尾。
- 网络代码不在异步回调里直接操作 Unity 的场景对象。
- 你能找到“建连、拆帧、识别玩家、移动、回到 Unity 显示”各自的代码入口。

其中协议边界适合小型自动测试；Unity 输入、画面、双进程退出必须实际运行观察。控制台测试通过不等于 Unity 场景已经验证。

## 8. 后续按需求生长

第一版之后再选：

- 为移动加入快照插值，再研究客户端预测与校正。
- 在确实需要判断连接活性时补心跳；重连后重新进入房间，再逐步考虑会话恢复。
- 增加第二种传输方式，再提取 TCP/WebSocket 的共同接口。Windows Socket 方案不能直接当作 WebGL 方案。
- 换用 UDP 传输高频状态时，重新明确可靠性、过期数据、拥塞与带宽策略。
- 增加第二种小游戏，检验框架是否真的能复用。
- 多房间和服务端并发复杂起来后，再读 GameFrameX 服务端的相关设计。

TCP 适合帮助第一版看清可靠消息流程，但丢包时会延迟后面的字节。运行起来后，我们会用可见现象解释这个取舍。
