# TinyGameNet 通信与代码设计

返回：[项目设计与学习路线](00_项目设计与学习路线.md)

> 这是逐阶段实现的约定。文中的类型名是拟定名称，不表示代码已经生成。各模块第一次需要时再介绍，不要求开工前背完。

## 1. 先用一次移动说明整体

玩家 A 按住右键：

```text
Unity 主线程读取按键
  → 形成 MoveInput（向右）
  → 编码为完整应用消息，排队发送
  → TCP 送到服务器
  → 服务器还原消息，把“连接 A 的输入”放入待处理队列
  → 服务器下一个模拟步更新 A 的位置
  → 发出包含所有玩家位置的 WorldSnapshot
  → 两个客户端收到并排队
  → 各自的 Unity Update 应用最新状态，更新画面
```

服务器不会相信客户端报告的最终位置。它根据连接查到玩家、检查输入，再用自己的速度和时间步长算位置。

## 2. 稳定后会有哪些代码

每个目录先只放当下需要的文件。共享包保存一份源码，由服务器项目引用，也由 Unity 的本地包引用，避免两边手动复制出不同版本。

```text
TinyGameNet/
├─ Packages/
│  ├─ com.tinygamenet.core/       通用连接、拆帧、消息包络
│  └─ com.tinygamenet.game/       本游戏的消息定义、生成类
├─ Server/                      监听、玩家会话、世界更新
├─ UnityClient/                 场地、输入、显示、Unity 适配
├─ Tools/                       协议生成命令
└─ Tests/                       消息边界与关键规则验证
```

| 拟定对象 | 保存什么、做什么 | 何时引入 |
| --- | --- | --- |
| `TcpConnection` | 一条已连接 TCP 的流、读取任务、发送队列和关闭状态 | M1～M2 收发代码出现后再整理 |
| `FrameCodec` | 编码长度和包头，增量还原完整帧 | M2 |
| `MessageCodec` | 根据消息类型把 Protobuf 对象与 payload 字节互转 | M3 |
| `ClientSession` | 服务端的一条连接，以及它获准控制的玩家编号 | M4 |
| `GameWorld` | 玩家位置、方向、分数；每个模拟步推进状态 | M5 |
| `ClientBridge` | 把网络收到的消息交回 Unity 主线程；转交客户端输入 | M4～M5 |
| `PlayerView` | Unity 角色的画面表示，按服务器状态更新 Transform | M4～M5 |
| `PendingRequests` | 请求编号到等待任务的映射，以及超时清理 | M7 |

`GameWorld` 不引用 `UnityEngine`，位置先用普通的 X、Z 数值表达。`PlayerView` 才知道 Transform 和材质。服务器没有场景对象，也不用调用 Unity 物理引擎。

## 3. TCP 字节怎样恢复成消息

M1 只观察字节。M2 起固定应用帧格式，M3 开始解释包头字段：

```text
[bodyLength:4][version:1][kind:1][messageType:2][requestId:4][payload:N]
```

单位都是字节。前缀以外的固定包头占 8 字节，因此 `bodyLength = 8 + N`，整个应用帧占 `4 + bodyLength`。payload 是 Protobuf 编码的业务内容；应用帧可能被多个 TCP 段承载。

例如 payload 有 12 字节，长度字段写 20，完整应用帧有 24 字节。

- 固定包头中的多字节整数使用大端序。Protobuf 内容按 Protobuf 自己的编码规则写，不能拿包头字节序去解释它。
- `version` 第一版为 1。收到不支持的版本时报告协议错误并关闭连接。
- `kind`：1=Request，2=Response，3=Notification。
- `messageType` 决定业务消息的形状和处理入口。
- 请求的 `requestId` 非零，响应带回同一个编号；通知使用 0。编号只在当前连接内关联，不能当作跨重连的业务去重凭据。
- `bodyLength` 合法范围先定为 8～65,536。完整帧最多 65,540 字节。

接收流程：

1. 累积足够的 4 字节长度前缀；一次读不满就继续读。
2. 验证长度后，再为本帧正文准备空间。
3. 正文收满后检查版本、kind、type，再反序列化 payload。
4. 保留下一帧的数据继续处理，不能假设一次 `ReadAsync` 就是一条消息。
5. 对非空读取请求，返回 0 表示流结束。若一帧尚未收全，记录“截断的帧”并清理连接；空闲但没关闭时继续等待。

具体实现可以先用“读满前缀、再读满正文”的小循环。稍后需要统一接口时再封装，先理解每次读到的数量。

## 4. 第一批只要四种业务消息

| type | kind / 消息 | 内容 | 接收方动作 |
| --- | --- | --- | --- |
| 1 | Request / `JoinRoom` | 昵称 | 服务器检查容量与昵称，给连接分配玩家编号 |
| 2 | Response / `JoinRoomResult` | 成功标记、玩家编号或失败原因 | 客户端结束加入等待；成功后开始发送输入 |
| 3 | Notification / `MoveInput` | 输入序号、方向 X/Z | 服务器根据来源连接识别玩家，保存最新有效方向 |
| 4 | Notification / `WorldSnapshot` | 服务器 tick、完整玩家列表（编号、昵称、位置、分数） | 客户端创建缺少的角色、更新已有角色、移除列表中不存在的角色 |

玩家编号由服务器分配，不从 `MoveInput` 中信任一个“我要控制的玩家 ID”。输入序号帮助判断是否比上次新；它不是 TCP SEQ，也不是请求编号。

服务器先给新连接排队发送加入响应，再发送世界快照。只有加入成功的连接才能提交移动。重复加入请求不会在同一条连接上创建第二个玩家。

第一版快照总是完整玩家列表。这样加入、退出和后加入者的初始世界都能使用同一份规则。以后玩家多了，再讨论只发送变化的成本与收益。

## 5. 时间由谁推进

以下是便于观察的初始参数，会根据运行效果调整：

- 输入采样：Unity 每帧读键盘，最多每秒 20 次发送当前方向；按键松开后尽快发送零方向。
- 服务端模拟：每秒 20 步，每步 0.05 秒。
- 世界快照：每秒 10 次，即每两步模拟发送一次。
- 移动速度：每秒 4 个场景单位，因此持续向右一模拟步移动 0.2 单位。

一模拟步收到 10 条输入时，先处理并保留最新有效方向，再按固定步长移动一次。收到更多消息不会多移动 10 次。

方向要检查数值有限，并把长度限制在 1 以内，避免斜着走更快。服务器用自己的单调时钟记录最近输入时间；超过初始阈值 0.5 秒没有新输入时，将方向归零，防止失联后一直走。

这个“停止移动”阈值与“判定玩家离线”不同。角色移除由连接关闭或单独的活动超时处理；M6 再观察误判与等待的取舍。计时不使用客户端提供的时间。

第一版收到快照就更新显示，所以可能看到跳动与输入延迟。后续插值改善画面，预测改善本机操作反馈；它们不会改变服务器最终决定状态的原则。

## 6. 异步收发与世界更新怎样相处

`await` 不承诺后续代码一定回到 Unity 主线程。我们用明确的交接规则：

- 每条连接只启动一个接收循环。
- 网络处理把完整消息放入有界队列，Unity 在 `Update` 取出后操作场景。
- 服务器也通过队列把连接事件与输入交给唯一的世界更新循环。只有这个循环修改玩家集合和位置。
- 所有出站消息经过该连接唯一的发送循环，避免多个调用同时把包头、正文交错写进流。
- 框架接管入队后的完整字节数组，调用者不再修改或复用它。

初始限制：每连接待发送总量不超过 256 KiB、待交给业务的消息不超过 256 条。超过限制时记录原因并断开该慢连接，其他玩家继续更新。实现时计入正在发送的那份数据，别只计算尚未出队的消息。

这些值是第一版的可调上限，并非通用最佳参数。Unity 每帧的业务消息处理量也设上限，避免大量入站消息独占一帧。

## 7. 关闭必须有负责人

连接可以处于 `Disconnected → Connecting → Connected → Closing → Disconnected`。客户端是否已经加入游戏，是另一个状态；TCP 连接成功还没有玩家身份。

由连接对象统一收尾：

1. 标记关闭，拒绝新发送。
2. 取消等待并关闭 Socket，让阻塞中的异步读取结束；观察收发任务的完成与异常，避免留下无人处理的后台任务。
3. 使仍在等待的请求失败，清空队列。
4. 发出一次关闭事件；重复关闭不重复通知。
5. 服务端世界循环处理该事件，移除对应玩家；客户端主线程显示断线提示。

退出 Unity Play Mode、关闭窗口、远端断开和解析失败，都走同一收尾路径。断线后的自动重连属于后续扩展；第一版可手动重新连接并重新加入，获得新的身份和全量世界。

## 8. 请求等待为什么最后抽出来

M3 先明确处理一种加入响应。等真实出现第二种请求时，再在 M7 抽出通用等待表：

```text
分配 requestId → 先登记等待任务 → 再排队发送请求
收到 Response → 按 requestId 找任务 → 完成并删除
超时或断线 → 令任务失败并删除
```

必须先登记再发送，防止很快的响应到来时还找不到等待任务。同一连接内不复用请求编号；空间耗尽时重建连接，避免迟到响应认错请求。请求超时只表示本机没及时得到响应，不能证明服务器没有执行。

“发消息并异步等待对应结果”常被封装成 RPC 调用。第一次看到这个词时，我们会用已经写好的等待表解释它。购买等业务的跨重试去重，仍需要独立的业务操作编号和服务器记录。

## 9. 必须验证的边界

协议：前缀分成四次到达、正文分批到达、两帧连续到达、长度为 7、长度超上限、正文截断、未知消息类型、payload 解析失败。

业务：未加入就移动、重复加入、伪造过大方向、消息发十倍快、后加入者、客户端退出、服务器退出、慢客户端。

请求：响应在超时后到来、两个响应与请求顺序不同、断线时仍有等待任务。

这些验证随相应阶段补齐。尚未实现的功能不会提前标记通过。
